# PDF 2.0 deltas

ISO 32000-2 items tracked against the 1.7 baseline as they become relevant.
Full 2.0 conformance is not a current goal ([architecture.md](architecture.md)).

| Delta | Status | Doc |
| --- | --- | --- |
| AES-256 / R6 encryption (was Adobe extension, core in 2.0) | Committed day one | [encryption](features/encryption.md) |
| R5 deprecated | Read-only with warning | [encryption](features/encryption.md) |
| Public-key AES-256 (7.6.5: `adbe.pkcs7.s5`, `/V 5`, an `AESV3` crypt filter) | **Read and written.** A host `Recipient` opens one; `PublicKeyEncryption::seal` and `DocumentEditor::save_sealed` write one, and nothing below `/V 5` is written | [encryption](features/encryption.md) |
| Document timestamps (12.8.5: `/Type /DocTimeStamp`, `/SubFilter /ETSI.RFC3161`) | **Read and written.** `DocumentEditor::save_timestamped` writes one around the token a host `Timestamper` returns, never drawn; the verdict validates the token's imprint against the covered bytes, its signature over its `TSTInfo`, its authority's certificate and its chain at `genTime` | [signatures](features/signatures.md) |
| The document security store (12.8.4.3: the catalog's `/DSS`, with `/Certs`, `/CRLs`, `/OCSPs` and `/VRI`) | **Read and written.** `add_validation_data` writes it from host-gathered DER, and a document below 2.0 also gains the `/ESIC` developer extension a 1.7 file declares the store with; `Document::security_store` reads it back as references. Surfaced and never evaluated: whether revocation data is fresh is a question with a clock in it | [signatures](features/signatures.md) |
| `adbe.pkcs7.sha1` deprecated (12.8.3.3.1) | **Verified, and called weak.** Both links of its encapsulated digest are checked and every such verdict carries `Weakness::Sha1Digest`. The writer never picks it; `SigningRequest::sub_filter` writes whatever the host names | [signatures](features/signatures.md) |
| UTF-8 string type | **Read and written.** `decode_text_string` takes 7.9.2.2's `EF BB BF` as UTF-8 wherever a text string is read; `encode_text_string` writes that form for a document declaring 2.0 or later when PDFDocEncoding cannot carry the text, and UTF-16BE below 2.0. Every text string the engine writes goes through it — `/Info`, outline titles, field values, a new signature field's `/T`, a note's `/Contents` — and `text_string_roundtrip.rs` reads them back byte-exact at 1.7 and at 2.0 | [document-model](features/document-model.md) |
| 2.0 blend/dash clarifications | **Tracked, and not readable here.** What ISO 32000-2 changed in 11.3.5 and 8.4.3.6 against 1.7 needs the 2.0 text, and on 26 September 2026 none of it could be read: the PDF Association's sponsored copy (`pdfa.org/sponsored-standards/`) was refused by this environment's egress policy with a 403, and a refused host is not routed around. Two first-party PDF Association sources were reachable and say less than the question needs. **Its errata** (`github.com/pdf-association/pdf-issues`, `docs/32000-2-2020/`, at `b25fc23`, 16 September 2026) carry nothing under 8.4.3.6, and under clause 11 only a NOTE that Figures 72 and 73 are indicative (issue 345), a symbol fix in 11.4.8 (688), `/ID` and `/OPI` deprecated in Table 143 (619) and Table 145's `/CS` defaults resolved in the group XObject's own resources (134); they quote only the text an erratum touches, by ISO copyright. **The Arlington model** (`github.com/pdf-association/arlington-pdf-model`, `tsv/latest`, at `c48b363`, 17 September 2026) records the array form of `/BM` as deprecated in 2.0 and `/Compatible` since 1.4 — both of which this engine already reads — and nothing about dash semantics. Nothing was implemented from memory. One thing the errata's quotation does say is recorded in the [ROADMAP](ROADMAP.md) row rather than acted on: Table 145's `/CS` text excludes Lab from a transparency group's colour space, so the `/Lab` group [rendering](features/rendering.md) composites in Lab is a file the specification does not permit, and what a reader does with one is a decision | [rendering](features/rendering.md) |
| Namespaced structure types (14.7.4, 14.8.6: an element's `/NS`, the root's `/Namespaces`, a namespace's `/RoleMapNS`) | **Read and written.** `DocumentBuilder::add_namespace` (refused below 2.0), `Tag::namespace` and `map_role_in` write them; `StructElement::namespace`, `standard_namespace` and `StructureTree::namespaces` read them, `/RoleMapNS` followed across namespaces. Implemented from what was citable here: the approved errata (`pdf-issues` at `b25fc23`) quote Tables 354 and 355, 14.8.6.1's default namespace `http://iso.org/pdf/ssn` and the role-map-first rule, and 14.8.6.2's EXAMPLE 1 `[/H1 11 0 R]`; the Arlington model (at `c48b363`) gives Table 356's keys and that a `/RoleMapNS` value may be a bare name; veraPDF's published PDF/UA-2 rules (`veraPDF-validation-profiles` wiki at `109b482`) give the 2.0 namespace's URI `http://iso.org/pdf2/ssn` and forbid a mapping within one namespace (8.2.4-3) or out of the standard ones (8.2.4-4), which the writer refuses. **Not stated in any of them, so not guessed:** which namespace a bare-name `/RoleMapNS` value means, and whether the global `/RoleMap` is withheld from an element naming a namespace — the reader reports `standard_namespace: None` for the first and keeps 1.7's behaviour for the second. The 2.0 namespace's own type list is not quoted, so only a target in the 1.7 namespace is checked against a list. Attribute namespaces (14.7.6) are not read | [content-and-text](features/content-and-text.md), [design/tagged-pdf](design/tagged-pdf.md) |
| Page-level output intents (a page's own `/OutputIntents`) | **Read and written.** `Page::output_intents` reads a page's own and `Document::output_intents` the catalog's, each an `OutputIntent` with Table 365's entries and the profile stream by reference; `PageBuilder::output_intent(NewOutputIntent)` writes one in a document declaring 2.0 and not under an archival profile, pages naming one profile sharing its stream. Sources: the Arlington model (at `c48b363`) lists `/OutputIntents` in its 2.0 `PageObject` table, not inheritable, with Table 401's keys; the PDF Association's `pdf20examples` (at `c20f2c1`, CC BY-SA 4.0, so not committed — the test's fixture is written by hand in its shape) carry a file whose page intent *"can override the output intent for the document in the catalog"*. **Not stated in either, so not done:** how a page's intents combine with the catalog's when their subtypes differ, so the two lists are handed back unmerged; and Table 401's other 2.0 keys (`/DestOutputProfileRef`, `/MixingHints`, `/SpectralData`) are neither read nor written. The PDF/A validator's own reading, which takes a part 4 page's destination when the catalog has none, is untouched | [document-model](features/document-model.md) |
| Associated files (14.13: an `/AF` array of file specifications, each with `/AFRelationship`) | **Read and written on the catalog, a page, a structure element, the structure tree root, a link annotation, a form XObject and a marked-content sequence; read from any other holder by reference.** `DocumentBuilder::associate_file`, `associate_file_with_structure` and `add_form_with_files`, `PageBuilder::associate_file`, `associate_file_with_link` and `with_associated_files`, and `Tag::associated_file` take a `NewAssociatedFile` and write an embedded file stream (`/Subtype` the MIME type, `/Params` with `/Size` and `/CheckSum`) under a specification carrying `/F`, `/UF`, `/Desc`, `/EF` and `/AFRelationship` — in a document declaring 2.0, or under ISO 19005-3, which carried them on 1.7 first; other archival parts refuse by `ArchivalRefusal::AssociatedFile`, and a part 3 document carrying one validates with no finding. `Document::associated_files`, `structure_associated_files` and `associated_files_of(reference)`, `Page::associated_files` and `annotation_associated_files`, and `StructElement::associated_files` read them back as `AssociatedFile`s, nothing defaulted. **14.13.5's marked-content form**, from the errata's amendment (Table 409a, *"Property list entries for associated files"*: `/MCAF`, an array of one or more file specifications each with `/AFRelationship`): `with_associated_files` writes `/AF /AFn BDC … EMC` with `<< /MCAF [...] >>` as a named `/Properties` resource, as the errata's EXAMPLE does, and `Page::marked_content_associated_files` lists each sequence the clause's last paragraph connects — the `/AF` tag with a *named* list defined by Table 409a, forms included — and nothing else. Sources: the approved errata (`b25fc23`) quote 14.13.1's *"AF entry that shall be an array of file specification dictionaries … that contain an AFRelationship entry"*, Table 44's `/Subtype` requirement and its MIME shape (no `;`, `=` or `#`), and the `EncryptedPayload` rule; the Arlington model (`c48b363`) the holders and `FileRelationship`'s eight values; veraPDF's published PDF/A rules (`109b482`) 6.8-1 and 6.9-1's MIME pattern, which the writer enforces. **Left:** `/AF` *written* on an annotation the builder does not make (it makes links), an image XObject or a document part, and on an existing document through the editor — each is read; `EncryptedPayload` is read and never written, since it needs an `/EP` dictionary (Table 44's encrypted payload) and no `/EP` writer is in reach | [document-model](features/document-model.md), [creation](features/creation.md) |
| Deprecated features (XFA removed in 2.0, /ProcSet, ...) | Noted per doc; XFA is a named permanent non-goal ([ROADMAP.md](ROADMAP.md)) | — |
